## 分清四个检查点

| 检查点 | 能证明什么 | 不能证明什么 |
| --- | --- | --- |
| 手机自动化运行 | 系统触发了动作 | HTTP 成功、dot 已接收 |
| `/ingest` 返回 202 | Bridge 已接受并持久化 | 回调送达、dot 已处理 |
| webhook 返回 2xx | 接收端确认投递 | dot 已逐条处理或执行后续动作 |
| dot 出现对应事件 ID 的处理结果 | 本次已由目标 dot 实际处理 | 所有未来事件、所有 App、长期零丢失 |

允许 dot 合并多个事件的回复；不能因为没有逐条聊天气泡就断言投递失败，也不能因为服务器 ACK 就断言所有内容已处理。

当前隔离云端检查已通过 MCP 按 UUID 匹配五条合成事件，投递统计为五次 accepted，重复重试没有新增记录。这提供存储、查询及接收端确认的证据，但尚不证明目标 dot 已处理这些事件或 iPhone 系统触发器运行，详见[日期化验证记录](validation-record.md)。

## 第一版历史验收

以下结果来自个人设备开发记录，截至 2026-10-01；本次整理源码公开材料不代表再次连接手机重测。公开版本只保留结论，不发布私人截图、事件 ID、联系人、通知正文或精确生活时间线。

- 一条合成事件曾通过云 Bridge 唤起原个人 dot，并出现匹配回执。
- iPhone 手动执行上传曾成功；随后部分微信、抖音、电话、QQ 邮箱的真实通知也自动送达原 dot。
- 微信既曾传入通用提示，也曾传入实际标题／正文；这是实际输入不同，不能从通用提示还原隐藏文字。
- 另一邮箱来源已有 Bridge 投递确认，但该次记录没有独立 dot 回执，因此不计入完整处理验收。
- 锁屏连接与断开充电器，分别上传了电量和 true／false 充电状态，均有 dot 回执。
- 三个选定 Focus 模式的六个开启／关闭方向曾通过真实切换和 dot 回执。
- 曾配置数十个 App 共用通知流程；没有逐一验证全部来源，也没有未来新 App 自动加入的证据。

本地测试的实际执行结果单独记于 [本版验证记录](validation-record.md)，不沿用早期测试数量冒充本次结果。

## 新安装的最小验收

1. 全新未配置候选先确认 `/setup` 可访问，`/health`、OAuth、MCP 和上传返回 `503`。按[部署指南](deployment.md)补齐配置后，再要求 `/health` `200`、未授权 `/mcp` 拒绝访问及上传关闭；检查 Worker 和 GitHub owner 都属于自己。健康检查 `200` 只表明最低 Origin／owner 配置有效，不证明全部 Secrets 已存在或正确。
2. 完成插件授权，由目标个人 dot 订阅 `phone.event`；查询 `phone_bridge_status`，确认存在有效期限。
3. 用不含私人信息的合成事件验证上传、签名回调和目标 dot 回执。不要把给 dot 手动发聊天消息当作事件推送测试。
4. 开启选定通知自动化，在手机实际收到测试通知时验证同一个 event_id 和来源；至少测试锁屏与后台状态。
5. 分别测试充电插入／拔出、每个 Focus 的开启／关闭；手动运行快捷指令只算诊断，不能代替真实触发。
6. 再测试 Wi-Fi／蜂窝切换、关闭代理的实际网络、短暂断网、重启后首次解锁、通知连续到达及系统摘要等场景。当前没有离线 outbox，应如实记录断网遗漏。
7. 检查订阅到期前的 `refreshBefore` 是否更新，并在跨过原到期点后验证真实新事件。只有时间到了，才能证明长期刷新；短 TTL 的本地用例不能代替真实平台续期。
8. 排除 ChatGPT、Codex 和快捷指令来源后观察是否有回传循环。断开插件连接并核实停止投递，以确认撤销边界。

建议用合成标记记录“产生、手机执行、Bridge 接收、dot 处理”四个时间点。单次上传快并不等于通知全程时延保证，也不能由有限样本推算稳定性 SLA 或省电幅度。

## 常见问题

| 现象 | 优先检查 |
| --- | --- |
| 自动化无法启用 | 是否没有选 App，或残留空的“标题包含……”条件；保存后重新打开核对 |
| 手动成功，自动触发没有数据 | 来源是否实际生成通知、首次“运行另一快捷指令”／域名访问权限、自动化开关、有效输入绑定 |
| app 错误或固定为某个 App | 是否使用当前通知的 App 属性，而不是硬编码或误选正文 |
| 时间只有日期没有时分秒 | ISO 8601 格式是否包含时间和时区 |
| JSON 类型错误 | 布尔值和数字是否用原生类型，payload 是否绑定整个字典 |
| 401／403 | 上传令牌是否属于该设备；读取是否误用了手机令牌；OAuth owner/scope 是否匹配 |
| OAuth 端点 413／414／400 | 核对[协议](protocol.md)中的请求体、编码查询及字段上限，修正客户端请求，不盲目放大限制 |
| OAuth 端点 429 | 读取并遵守 `Retry-After`，等待该路由预算窗口；反复重新连接也会消耗准入额度 |
| 503 | 初装未配置阶段属于预期；补齐后检查必要配置、`ENABLE_INGEST`、设备启用状态，以及返回的固定 OAuth guard 错误类别 |
| Bridge 接受但 dot 没响应 | 订阅有效期、投递状态、权限撤销及 dot 异步处理情况；必要时分页补查 |
| 续期后仍漏掉旧事件 | 当前实现不支持 cursor replay，也不为订阅断档期间事件自动创建补推任务 |
| 浏览器打不开授权页 | 分开检查浏览器、网络、域名、OAuth callback；不要先猜是某个代理插件，也不要关闭 TLS 校验 |
| 同意 POST 失败或显示 `ERR_BLOCKED_BY_CLIENT` | 检查真实 POST Origin 和 Worker 响应。本次隔离测试中 `no-referrer` 导致 `Origin: null`，Worker 返回 `403`；同意页改为 `same-origin` 后浏览器流程通过。继续拒绝 null／跨站 Origin，并保留 cookie 检查。独立请求 `302` 仍不足，需原客户端实际完成 GitHub callback 并显示预期 OAuth 连接 |
| 既有 Worker 的设置页提示生成新凭据 | 停止应用新值；`/setup` 面向全新部署，不是 registry 替换或密钥轮换工具 |

源码测试使用合成 token 与隔离回调，不验证真实网络路由、手机后台策略、实际 GitHub 登录或账号中的 dot 可用性。
