# 常见问题：身份、网络、续期与交付

[English](../faq.md) | [简体中文](faq.md) · [首页](../../README.zh-CN.md)

原始整理日期：2026-10-02；浏览器优先候选版说明补充于 2026-10-08，实验性 Beta 状态更新于 2026-10-12。当前安装说明对应 `v0.1.0` 正式版。实现事实以本仓库源码为准；外部平台规则可能变化。本文没有把本地代码测试当作线上稳定性测试。

## 为什么手机事件会出现在个人 dot 中？

手机并没有把文字粘贴进聊天窗口。系统快捷指令把选定事件转换为 JSON，使用设备上传令牌发送到自己的 Bridge；Bridge 保存事件，再根据 dot 已建立的订阅发送签名 webhook。ChatGPT 接收事件并异步交给该订阅关联的助理处理。

通知中如果包含消息正文，正文就能成为事件的一部分。没有通知、系统未交付正文或没有配置该来源，就没有可转发的内容。SMS 应单独配置 Message 或适用的通知触发器并验收，不能由其他 App 通知成功推断短信全部可用。详见[架构](architecture.md)。

## GitHub 里的“验证”有什么作用？

第一版连接过程中出现的 GitHub 授权，是 **OAuth 身份验证**：

1. 用户通过 GitHub 登录，Bridge 获取其公开用户身份。
2. Bridge 将返回的数字 ID 与部署配置中的唯一 owner 比较。
3. 一致时，Bridge 完成自己的授权流程，让客户端取得读取及订阅手机事件的权限。

这相当于确认“谁有权连接这台 Bridge”。代码不申请 GitHub 仓库权限，不把通知上传到 GitHub，不把 GitHub token 放进手机，也不持久保存上游 GitHub token。设备上传、Bridge OAuth、webhook 签名是三套不同凭据，见[安全说明](../../SECURITY.zh-CN.md)。GitHub 的授权机制参考[官方 OAuth 文档](https://docs.github.com/en/apps/oauth-apps/building-oauth-apps/authorizing-oauth-apps)。

源码仓库用于分享代码，GitHub OAuth 用于身份确认，两者可以独立存在。若以后在仓库增加 GitHub Actions 的测试绿勾，那是代码检查；它不证明手机正在转发。CI 的实际结果应以当前工作流及该次运行输出为准。

后续可以替换身份提供方，但要保留 owner 绑定和最小权限，不能通过去掉认证来“简化”。

## 需要购买域名、保持 Mac 开机或使用终端吗？

无需购买域名，默认使用 Worker 的 `workers.dev` 地址。浏览器主路径是 Cloudflare 官方部署、自己的 `/setup`、控制台配置、自己的 GitHub OAuth App、dot 连接及 Notifications 通知快捷指令，不要求本地安装 Node.js 或使用终端。开发与恢复仍保留[高级 CLI 路径](deployment.md)。

日常转发不需要 Mac 或 iPhone 镜像常开；镜像可辅助创建和检查快捷指令，但不是部署后的采集机制。当前安装路径仅提供 Notifications 通知模块。Charging、Focus On 和 Focus Off 均标记为**即将推出**，不属于当前配置或验收范围。历史 v0.1.0 发布保留了原 Beta 的四份签名文件，但历史发布记录不能证明所有模块当前都可用。此前观察到的导入路径使用 Mac 和同账号 iCloud 同步；直接 iPhone 导入及独立账号复现仍需分别验收。按[安装指南](iphone-shortcuts.md)配置通知模板和真实触发器即可；模板自带 HTTP 上传动作，无需再搭建旧辅助快捷指令。各日期的结果与边界仍保留在[验证记录](validation-record.md)。

## 在中国大陆，手机不开 VPN 能不能发送？

**从链路结构看有可能，当前材料没有证明在大陆实际网络上稳定可用。** 请求分为两段：

```text
手机 → 自己的 Bridge HTTPS 入口
Bridge → ChatGPT 的事件接收端
```

第一段没有要求手机直接连接 ChatGPT。只要手机当前网络能正常解析并访问 Bridge，上传就有可能完成；第二段由云端发起。但 Cloudflare 部署、自定义域名或海外服务器本身都不保证第一段的可达性、延迟或成功率。初次登录、连接和授权又有自己的网络依赖。

同时，网络能通不等于平台提供服务。截至整理日期，中国大陆未列入 ChatGPT 官方支持地区；官方说明也提示，在列表外访问或提供访问可能导致账号受限。这个 Bridge 不改变平台支持范围，不能宣传为地区可用性的保证。[ChatGPT 支持地区](https://help.openai.com/en/articles/7947663-chatgpt-supported-countries)

若要验证上传链路，应在本人实际 Wi-Fi 和蜂窝网络、关闭代理的条件下，用一条无私人内容的真实触发事件，分别核对手机触发、Bridge 保存、webhook ACK 和 dot 回执。只打开 `/health`、只测电脑或只看到 `202` 均不够。首次接入成功也不能代表之后每个网络都稳定。

## 配置好以后，放着就能一直转发吗？

设计上是事件触发后自动运行，无须每天手动逐条转发，也不需要 Mac 常开。持续工作仍依赖以下条件：

- 手机能运行相应自动化，来源 App 实际产生事件，所需授权和来源选择保持有效。
- 手机能访问 Bridge，设备凭据有效，服务端上传开关保持开启。
- 云资源、域名和 HTTPS 正常，容量和平台配额没有阻断处理。
- dot 的连接授权有效，事件订阅按时刷新，接收端和助理正常处理。

目前不能承诺无人维护地永久运行。已有真机成功记录，但没有完整的跨日续订、长期弱网、系统更新、重启后恢复或突发通知可靠性验收。手机离线队列也未实现；手机没上传成功的事件不能靠服务端重试补回来。

正常使用不需要每天重新部署。初期应完成至少一次跨越 24 小时订阅周期的真实验收；系统更新、修改自动化、换账号或域名后再做一次小规模回归。发现转发中断时按[验证与故障定位](verification.md)查看最近事件、订阅期限和投递状态。这里没有安装额外的定时监控或自动续期任务。

## “订阅”和“续期”是付费吗？

这里的订阅是 dot 向 Bridge 登记“收到哪些设备、哪些类型的新事件时通知我”。它是一条**有期限的事件接收登记**，不表示购买会员。

当前代码每次默认授予 24 小时，最长也为 24 小时，返回 `refreshBefore` 表示期限。接收客户端应在期限前再次调用 `events/subscribe`，延长同一登记的有效期。这是代码中的生命周期安排，不是 iPhone 的一天限制，也不是 ChatGPT 会员到期。官方协议说明 ChatGPT 会刷新将到期的订阅；本项目仍需用真实跨日结果验证当前连接的实际行为。[MCP Events 生命周期](https://developers.openai.com/plugins/build/mcp-events)

没有续上时，若上传开关、设备和云服务仍正常，手机仍可将事件保存到 Bridge；过期登记不再投递。随后重新订阅不会自动回放断档期间的事件，本版可在保留期内通过查询工具读取。不要因为嫌续期麻烦而直接承诺“永久订阅”；更长租期或协议 replay 都需要单独实现、撤销机制与测试。

云平台、域名或 ChatGPT 自身的费用是另一回事，不能据此承诺整个方案永久免费。

## 这是最简单的方案吗？有没有一站式替代？

在“iPhone 自动采集、云端保存、主动交给原个人 dot”这个目标下，第一版是一条已部分实测的路径，不能称为所有方案里绝对最简单。应先明确要保留哪些结果：

| 路线 | 减少的工作 | 仍需承担的部分 |
| --- | --- | --- |
| 当前自托管 Bridge | 有现成源码和协议，无须自写原生 App | 云资源、身份连接、手机自动化配置和维护 |
| 干净快捷指令模板＋配对向导 | 减少手工拼字典和复制参数 | 系统权限、来源选择、dot 资格与生命周期验证 |
| Swift 伴侣 App＋App Intents | 收拢凭据、发送逻辑、队列和诊断 | 仍需系统触发器；开发、分发与后台生命周期约束 |
| n8n、Make 或自建 webhook 工作流 | 可承接 HTTP、存储和部分自动化编排 | 不能凭编排平台获得 iPhone 通知权限；进入原 dot 仍需兼容接收接口 |
| 自建 API 助手作为消费者 | 可以自行控制助理逻辑和存储 | 另行开发认证、状态与事件处理；不等于原个人 dot |

后两行是替代架构的评估方向，本仓库未集成、未测试具体产品，也没有证明某个现成服务能一键替换所有层。[n8n Webhook](https://docs.n8n.io/integrations/builtin/core-nodes/n8n-nodes-base.webhook/) 和 [Make Webhooks](https://help.make.com/webhooks) 的官方文档只证明它们能承接 HTTP 事件，并不证明能直接对接个人 dot；托管方式还会增加一个处理通知内容的服务方。普通“发给模型取得回答”的 API 调用，不自动进入原 dot 的上下文。

DotLink 当前仅引导安装 Notifications 通知模块。下一步是独立通知安装与真实触发验证，再补充配对、状态与恢复能力。Charging、Focus On 和 Focus Off 在单独验证并发布前继续标记为即将推出。具体顺序和验收条件见[简化路线](roadmap.md)。
